# 双容器评测 Observation / Action 同步问题修复说明

本文记录双容器评测中 observation 和 action 不同步问题的原因、影响和修复方式。

## 1. 问题背景

当前评测系统采用双容器架构：

- `sim-eval` 容器负责 Isaac Sim 场景、机器人控制、observation 采集和任务断言。
- `infer` 容器负责加载 policy，接收 observation 后推理 action。
- 两个容器通过 WebSocket 传输 observation 和 action。

单步评测链路如下：1

```text
sim-eval 采集 observation
  -> WebSocket 发送给 infer
  -> infer 执行 policy 推理
  -> WebSocket 返回 action
  -> sim-eval 执行动作并推进仿真
```

如果 infer 推理耗时较长，或者 sim 侧在等待 action 时继续推进场景，就会出现 action 对应的是旧 observation，但执行时场景已经变成新状态的问题。表现上会像通信延迟变大，机器人动作慢半拍或一拍，严重时会影响任务成功率和断言结果。

## 2. 原有问题

### 2.1 `

`WalkerS2sim.send_action(action)` 在推理/回放模式下会做两件事：

1. 将 action 写入 `_pending_absolute_action`。
2. 调用 `self.step(render=True)` 推进一次 Isaac 物理仿真，让 physics callback 消费 pending action。

因此，`send_action(action)` 本身已经完成了一次动作应用和仿真推进。

原先 `ghrc_eval_sim.py` 在调用 `self.robot.send_action(action_dict)` 后，又额外调用了一次：

```python
self.robot.step(render=True)
```

这会导致一个 policy action 对应两次仿真推进。下一次采集 observation 时，场景已经比 action 对应的时间点多走了一帧，造成 observation/action 时间错位。

### 2.2 等待 infer 推理期间场景可能继续更新

双容器评测中，`sim-eval` 在发送 observation 后会等待 infer 返回同一 `episode_id` 和 `step` 的 action。

如果等待期间 Isaac world 仍在播放或被其他更新机制推进，场景状态会继续变化。此时 infer 返回的 action 是基于发送时的 observation 推理出来的，但 action 实际执行时，仿真环境已经不是那一帧状态。

这类错位不是简单的网络慢，而是控制闭环中的时序不一致：

```text
obs_N 发送给 infer
  -> infer 正在推理
  -> sim 场景继续更新到 N+k
  -> action_N 返回
  -> action_N 被应用到 state_N+k
```

## 3. 修复内容

### 3.1 移除 `send_action()` 后的额外 `robot.step()`

修改文件：

- `src/lerobot/scripts/ghrc_eval_sim.py`

修复后，评估循环只调用：

```python
self.robot.send_action(action_dict)
```

不再额外调用：

```python
self.robot.step(render=True)
```

原因是 `WalkerS2sim.send_action(action)` 内部已经推进一次物理仿真，外层重复推进会造成一个 action 执行两帧。

### 3.2 等待 action 期间暂停 Isaac world

修改文件：

- `src/lerobot/scripts/ghrc_eval_sim.py`
- `src/lerobot/robots/walker_s2_sim/walkers2sim.py`

在 `WalkerS2sim` 中新增两个薄封装：

```python
def pause_simulation(self) -> None:
    pause = getattr(self._world, "pause", None)
    if callable(pause):
        pause()

def resume_simulation(self) -> None:
    play = getattr(self._world, "play", None)
    if callable(play):
        play()
```

在 `ghrc_eval_sim.py` 中，发送 observation 后暂停仿真，等待 action 结束后恢复仿真：

```python
self.ws_client.send_observation(...)

pause_simulation = getattr(self.robot, "pause_simulation", None)
resume_simulation = getattr(self.robot, "resume_simulation", None)
if callable(pause_simulation):
    pause_simulation()
try:
    action_message = self.ws_client.wait_for_action(...)
finally:
    if callable(resume_simulation):
        resume_simulation()
```

这里使用 `finally` 是为了保证即使等待 action 超时或抛出异常，Isaac world 也会恢复到可继续运行的状态，避免后续 reset 或清理流程卡在暂停状态。

## 4. 修复后的单步时序

修复后，每个 step 的时序为：

```text
get_observation()
  -> flatten_obs()
  -> send_observation(step=N)
  -> pause_simulation()
  -> wait_for_action(step=N)
  -> resume_simulation()
  -> send_action(action_N)
       -> 写入 pending action
       -> 内部 step 一帧
       -> physics callback 消费 action_N
```

这样可以保证：

- infer 推理期间场景不继续向前漂移。
- `action_N` 对应的是发送给 infer 的 `observation_N`。
- 一个 action 只推进一帧仿真，避免额外 frame skip。

## 5. 后续注意事项

如果后续做以下改造，需要重新检查 observation/action 对齐关系：

- action chunk 或异步推理。
- sim 和 infer 合并到单容器或单进程。
- 将 `send_action()` 改成只写 pending、不负责 `step()`。
- Isaac world 更新方式从显式 `world.step()` 改成后台实时播放。

推荐保持一个清晰约定：每个评测 step 只采一次 observation，只接收同 step 的 action，并且只推进一次物理仿真。
